# Архитектура и контракты

```text
Vue / Pinia
  | same-origin HTTP(S), WebSocket
Nginx
  | /api/auth/* -> Go Auth -> Redis session revocation
  | /api/v1/*, /ws -> Elixir Bandit / WebSock
  |                    | Bearer JWT
  |                    v
  |                  Rust Axum
  |                    | Go Auth /api/auth/users/me
  |                    | Diesel / r2d2 / PostgreSQL
  |                    | Gemini function calling: preferences
  |                    | Gemini Google Search: cited venue research
  |                    | Gemini JSON schema: constrained extraction
  |                    | Photon: address coordinates
```

## Полный стек

`infra/docker-compose.gastro.yml`, переменные в `infra/.env`, шаблон `infra/.env.example`. Запуск: `bash scripts/compose.sh app up --build -d`. Наружу опубликован только Nginx на `127.0.0.1:8088`.

Vue 3, Composition API, Pinia и Tailwind управляют чатом, историей, темами gruvbox/paper, карточками и выбранным слотом. Карта в интерфейсе не отображается и браузер не загружает картографические тайлы.

## Поиск с привязкой к источникам

По умолчанию `LLM_PROVIDER=gemini`, `PLACES_PROVIDER=gemini`, `GEMINI_MODEL=gemini-3.8-flash`, `GEMINI_API_MODE=interactions`. Серверный Gemini transport находится в `gemini.rs`. Используется актуальный Interactions API с `store=false`: удалённая история взаимодействий не запрашивается, контекст хранится в нашей PostgreSQL. Старый формат generateContent включается явно через `GEMINI_API_MODE=generate_content`. Нормализатор поддерживает ответы обоих форматов.

`LLM_PROVIDER=ollama` переключает разбор предпочтений через `llm.rs` на `ollama.rs`: `POST /api/chat`, `stream=false`, `think=false`, `format` содержит параметры существующей схемы `query_places`. По умолчанию модель `qwen3:4b`, температура 0, контекст 8192, максимум 2048 генерируемых токенов. Принимается только завершённый ответ с JSON-объектом; некорректный/обрезанный ответ не изменяет профиль. Контекст и история передаются в том же ограниченном объёме, что Gemini. HTTP-ошибки и недоступность Ollama обрабатываются без логирования содержимого диалога. Таймаут Ollama 180 секунд, настраивается через `OLLAMA_TIMEOUT_SECS` в диапазоне 1–210 секунд.

Источник заведений остаётся независимым от `LLM_PROVIDER`. Для работы без внешних API используется явный `DEMO_PLACES=true`: геокодирование и поиск пропускаются, данные помечены демонстрационными. Реальный поиск использует прежние Gemini/Google Search или Яндекс. `scripts/compose.sh ollama` добавляет сервер Ollama и одноразовую загрузку модели из `infra/docker-compose.ollama.yml`; engine ждёт успешного скачивания. Веса сохраняются в отдельном volume. `OLLAMA_GPU=true` добавляет NVIDIA GPU через `infra/docker-compose.ollama-gpu.yml`. Базовый стек также поддерживает Ollama на хосте через `host.docker.internal`.

1. `query_places` извлекает частичные изменения профиля и слотов через function calling. Уже известные общие или заданные для каждого слота предпочтения не спрашиваются заново. Пользовательские сообщения и страницы передаются как данные, а не системные инструкции.
2. Photon геокодирует пользовательскую локацию. Центр берётся из геосервиса, не из ответа LLM.
3. Один исследовательский запрос Google Search получает параметры всех слотов, ищет реальные места, меню, часы, средний чек и датированную афишу. В запрос не передаются JWT, email, аккаунт или вся история чата.
4. Grounding metadata нормализуется: источники и фрагменты с цитатами. Interactions использует `url_citation` с символьными диапазонами; legacy — `groundingChunks`/`groundingSupports`. Нецитируемый текст не подтверждает факты.
5. Отдельный structured-output запрос извлекает записи по `schemas/search_results.json`. Он не включает инструмент поиска и не придумывает координаты или загрузку.
6. Валидатор требует подтверждённые название и адрес в цитате. Для кухни, среднего чека, расписания, меню и событий нужна соответствующая field evidence. Индекс источника обязан совпадать с цитируемым фрагментом, цитата — реально содержаться в нём. Число среднего чека проверяется в цитате, ссылка — в цитате или URL источника; событие должно иметь явно указанную дату и название. Неподтверждённые поля удаляются. Это проверка происхождения и согласованности, а не гарантия достоверности или актуальности страницы.
7. Адрес каждого принятого кандидата геокодируется Photon с координатной привязкой к центру поиска. Ответ только на уровне города/района не принимается за адрес заведения. Координаты приблизительны и показываются как полученные по адресу. Неразрешимые адреса пропускаются с пояснением.
8. Применяются исходные hard filter и формулы A/B. В выдачу попадают только прошедшие фильтры места.

Не более 12 записей на план и 5 кандидатов на слот. ID стабилен по имени и адресу (UUID v5); повторяющиеся записи одного слота удаляются. Релевантность для веб-поиска — относительный порядок кандидатов, а не официальная метрика Google или рейтинг отзывов. Загрузка от LLM не принимается: без отдельного достоверного источника используется L=0.5 и `load_estimated=true`.

`GroundingReport` сохраняет provider, checked_at, источники, поисковые запросы, предупреждения и HTML Search Suggestions. Источники доступны рядом со слотом, field evidence — внутри карточки. Search Suggestions показываются в sandbox iframe без разрешения скриптов; HTML не вставляется в DOM основного приложения через v-html. Все кликабельные ссылки проверяются как HTTP(S).

Контракты провайдера: [Google Search](https://ai.google.dev/gemini-api/docs/google-search), [Function calling](https://ai.google.dev/gemini-api/docs/function-calling), [Structured output](https://ai.google.dev/gemini-api/docs/structured-output), [Interactions](https://ai.google.dev/gemini-api/docs/interactions). Инструмент Google Search использует доступ и квоту Gemini-проекта; отдельного ключа Google Maps нет. Квота, регион и модель проверяются самим провайдером. При 429, неподдерживаемом регионе, неверном ключе или снятой модели сервер возвращает понятную ошибку и не подменяет выдачу фикстурами.

## Геосервисы

`GEOCODER_URL` по умолчанию `https://photon.komoot.io/api/`. Используется только поиск конкретного пользовательского запроса и небольшого списка адресов. User-Agent идентифицирует приложение; общий для процесса кеш содержит до 2048 результатов на 24 часа, доступ к публичному endpoint последовательный с интервалом не менее 1.1 секунды. На HTTP-вызов отведено 8 секунд. Публичный Photon имеет ограничения на разумную нагрузку и не даёт SLA: [политика сервера](https://github.com/komoot/photon#demo-server). Для нескольких реплик или большой нагрузки требуется собственный экземпляр/другой поставщик, публичный лимит не распределён между процессами.

Интерфейс не загружает карту или тайлы. Photon остаётся серверным геокодером и нужен для получения координат адресов, чтобы применять фильтр радиуса.

Старый адаптер поиска Яндекса сохранён опционально: `PLACES_PROVIDER=yandex` требует серверного ключа. Обогащение `PLACE_ENRICHMENT_URL` относится к этому legacy-провайдеру и не требуется новому поиску. Yandex Search передаёт ID организаций в доверенный endpoint, который может вернуть дополнения по `PlaceCandidate`; неизвестные поля не угадываются.

## Авторизация

Go Auth выпускает Ed25519 JWT с `user_id`/`session_id`. Ядро перед каждым защищённым запросом вызывает `/api/auth/users/me`: существующий сервис проверяет подпись, срок и Redis blacklist. Затем требуется `status=active`, а `owner_id` берётся из проверенного user_id. Владелец из тела запроса не принимается. При недоступности Auth доступ закрыт.

Gateway проверяет сессию до `ready`, а ядро повторно проверяет её для каждого сообщения. Браузер передаёт токен первой WS-frame, а не в URL. До авторизации действует таймаут 10 секунд; Origin проверяется по точному allowlist со схемой и портом. JWT и refresh token находятся только в памяти Pinia, localStorage используется для темы. После перезагрузки требуется повторный вход.

В Go Auth исправлен предел bcrypt: пароль вместе с длинным pepper и солью мог превышать 72 байта и ломать регистрацию. Новые хэши используют версионированный HMAC-SHA256 prehash с pepper и солью, закодированный в base64 перед bcrypt. Проверка старых bcrypt-хэшей сохранена; ранее сохранённые аккаунты не требуют миграции. Смена pepper по-прежнему несовместима со старыми паролями и не должна выполняться при обычном перезапуске.

## REST и WebSocket

Все `/api/v1/*` требуют `Authorization: Bearer ...`.

- `POST /api/v1/conversations` с `{}` создаёт диалог.
- `GET /api/v1/conversations?offset=0` возвращает до 30 диалогов, без полного документа.
- `GET /api/v1/conversations/{uuid}` возвращает `id,title,document,version,updated_at`, включая сообщения, профиль и карточки.
- `POST /api/v1/conversations/{uuid}/messages` принимает `{request_id:uuid,text:string}` и возвращает assistant frame.
- `POST /api/v1/rank` принимает [пример](rank-request.json), возвращает `{slots:[SlotResult]}`. До 12 уникальных слотов и 500 кандидатов, до 10 результатов на слот.
- `GET /api/v1/session` проверяет сессию.
- `GET /health` ядра проверяет PostgreSQL; gateway проверяет свой HTTP-процесс.

Клиент отправляет:

```json
{"type":"auth","token":"ACCESS_JWT"}
{"type":"message","conversation_id":"UUID","request_id":"UUID","text":"Рамен завтра в 14:00"}
{"type":"ping"}
```

Сервер отвечает `ready`, `thinking`, `assistant`, `error`, `pong`. Assistant содержит `text`, массив `dynamic_buttons:[{label,value}]`, массив `slots:[{slot,cards,rejected,dynamic_buttons,text,grounding}]`, request_id, conversation_id и время. Карточка содержит PlaceCandidate, slot_id, score и breakdown. Ошибка содержит `type:error,text,status,request_id`; malformed frames могут не иметь request_id.

Одна выполняемая supervised task на соединение; WS остаётся отзывчивым, повторная работа ограничена ответом 429. Максимум frame 16 KiB, idle timeout 300 секунд, heartbeat каждые 30 секунд. Bearer передаётся в ядро, тяжёлая работа не выполняется в callback WS.

## Хранение и конкуренция

В PostgreSQL хранится JSON-документ диалога с owner_id. Успешный ответ сохраняется атомарно вместе с пользовательским сообщением и обновлённым профилем. Повторный request_id возвращает ранее сохранённый ответ. Compare-and-swap версии не даёт вкладкам перезаписать изменения: конфликт возвращает 409, после которого нужно перечитать историю. Внешние запросы не удерживают DB-транзакции. Неуспешная генерация не сохраняет незавершённую пару сообщений; её можно повторить тем же ID.

До 4000 символов на сообщение и 200 пар на диалог. Для Gemini передаются последние 20 текстовых сообщений без предыдущих карточек. r2d2 pool 12, синхронный Diesel вызывается через spawn_blocking. Embedded migrations применяются до запуска HTTP listener.

## Фильтрация и оценка

Радиус проверяется по haversine. Заведение должно быть открыто весь слот; смежные окна работы объединяются, ночные окна поддерживаются. Неизвестные часы исключают место; кухня и чек обязательны только при соответствующих ограничениях. Пустой список кухонь означает любую, `max_price_rub:null` — нет лимита. В LLM-профиле явный нулевой бюджет означает отсутствие лимита и преобразуется в null. Слот имеет конкретную дату, RFC3339 offset и IANA timezone; максимальная длина 24 часа, смещение проверяется по timezone.

Сценарий A определяется `requires_event=true`, даже если событий не найдено. Веса: relevance 20, website/menu 20, load 20, event 40. Подтверждённое меню с ценами — 20, базовый сайт/меню без цен — 10. Событие с пересечением времени и совпадением интересов — 40, фоновое пересекающееся событие — 20, отсутствие — 0.

Сценарий B: relevance 40, website/menu 30, load 30. Меню — 30, базовый сайт — 15. Load вычисляется за весь слот с весом длительности; неизвестные участки получают 0.5, невалидные наблюдения игнорируются. Баллы загрузки — `weight*(1-L)`. Пересекающиеся наблюдения усредняются. Общая оценка 0–100; сортировка по баллу и затем стабильному ID. Округление только при отображении. Высокий балл не компенсирует hard filter.

## Эксплуатация и проверки

Connect timeout 5 секунд; Google Search до 70 секунд, остальные запросы Gemini до 40 секунд; общий deadline ядра 240 секунд, gateway 250 секунд, frontend REST 260 секунд. Body ограничен 2 MiB, Nginx ограничивает запросы по IP. API-ключи и тела ответов провайдера не пишутся в логи. TLS, backup PostgreSQL, настройки SMTP, аккаунтные квоты и сроки хранения требуют конфигурации для публичного размещения. Распределённые квоты Gemini по аккаунтам не реализованы.

Тесты покрывают скоринг, фильтры, ночные часы, неизвестную загрузку, оба формата Gemini, привязку цитат, отбрасывание неподтверждённых данных, HTTP auth и координируемый mock-конвейер поиска. `scripts/check-gastro.py` проверяет реальный локальный стек на временных аккаунтах без отправки писем. Флаг `--include-gemini` выполняет одно настоящее сообщение и отдельно сообщает ограничения провайдера.

## Презентационный режим

`infra/docker-compose.presentation.yml` запускает только frontend на `8090`. Готовые фикстуры находятся в `frontend/src/presentation/plan.js`. Авторизация, Gemini, геосервисы и WebSocket не вызываются. Запросы к backend не обходят авторизацию: они вообще не выполняются. Данные явно демонстрационные, история в памяти, перезагрузка возвращает исходный сценарий. Презентация доступна также через `npm run demo`, кнопку в интерфейсе или `?demo=1`.


## Восстановление SMTP для этого окружения

Установлена причина прежнего EOF: IPv4 Gmail SMTP не возвращает приветствие, IPv6 доступен, но отсутствует в Docker bridge. При `SMTP_HOST_NETWORK=true` скрипт запуска добавляет `infra/docker-compose.smtp-host.yml`: только notif переходит в host network, NATS доступен ему через 127.0.0.1:14222. Настройка Linux-specific и отключена по умолчанию в шаблоне. Auth продолжает использовать NATS по внутреннему имени nats.

`SMTP_NETWORK=tcp6` явно выбирает IPv6; поддерживаются также tcp/tcp4. `SMTP_TIMEOUT` задаёт ограничение соединения и SMTP-сессии (по умолчанию 20s). STARTTLS обязателен с проверкой сертификата и TLS не ниже 1.2. Ошибки подписаны по этапам; секреты не логируются. После принятия DATA сервером ошибка QUIT не вызывает ложного сообщения о неотправленном письме. Команда `notif --check-smtp` проверяет только соединение, TLS и AUTH, без MAIL/RCPT/DATA.


## Сетевая диагностика и DNS

`gastro-engine --check-upstreams` выполняет ограниченные по времени GET-проверки используемых сервисов до инициализации PostgreSQL. При `LLM_PROVIDER=ollama` проверяется `/api/tags`; при `DEMO_PLACES=true` геокодер и поиск не проверяются. В Gemini не передаётся ключ и не вызывается генерация: HTTP 400/401/403/429 показывает только доступность HTTP. Эта команда помогает отличить DNS/HTTPS-проблему от недоступной модели или квоты.

Модуль upstream регистрирует имя провайдера, операцию, тип сетевой ошибки и HTTP-статус. URL удаляется из reqwest::Error перед логированием; заголовки, ключи, тексты запросов и сырой ответ API не логируются. Таймауты возвращают 504, DNS/некорректный ответ — 502 с понятной причиной. Стандартный trace остаётся сводной строкой, подробности пишутся отдельно. Ошибки чтения тела по таймауту тоже классифицируются как таймаут, а не как невалидный JSON.

При `APP_CUSTOM_DNS=true` скрипт Compose подключает `infra/docker-compose.dns.yml` для engine и notif, с настраиваемыми APP_DNS_PRIMARY/APP_DNS_SECONDARY. По умолчанию выключено: публичные DNS не подходят для каждой корпоративной/VPN-сети. Парсинг bool-флагов не выполняет source/eval файла с секретами.
